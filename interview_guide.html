4. The Concurrency & Deadlock-Free Transfer Pipeline

Interview Goldmine: Interviewers frequently probe: "What happens if User 1 transfers from A ➔ B while User 2 transfers from B ➔ A at the same millisecond?"
[STEP 1: INGESTION] TransferRequest arrives: Source="ACC-A", Target="ACC-B", Amount=$500 │ [STEP 2: PRE-CHECK] Validate Source != Target (reject identical account transfers) │ [STEP 3: ID LOOKUP] Read Account IDs without lock: ID(A)=101, ID(B)=205 │ [STEP 4: DETERMINISTIC ORDERING STRATEGY] │ Compare primary keys numerically: (101 < 205) │ Always acquire lock on MIN(ID) first, then MAX(ID) second! │ [STEP 5: PESSIMISTIC LOCK ROW 1] SELECT * FROM accounts WHERE id = 101 FOR UPDATE; │ ──> Database locks Account 101 row exclusively │ [STEP 6: PESSIMISTIC LOCK ROW 2] SELECT * FROM accounts WHERE id = 205 FOR UPDATE; │ ──> Database locks Account 205 row exclusively │ [STEP 7: VALIDATE PRECONDITIONS] │ • Assert Account A is ACTIVE and Account B is ACTIVE │ • Assert Account A Balance ($1,200) >= Transfer Amount ($500) │ [STEP 8: ATOMIC MUTATIONS] │ • Account A: $1,200 - $500 = $700.00 │ • Account B: $300 + $500 = $800.00 │ • Save both accounts to persistence context │ [STEP 9: IMMUTABLE AUDIT LOG] │ • Insert Transaction record (Ref: "TRF-8F2B9C...", Post-Balance: $700.00) │ [STEP 10: COMMIT & RELEASE] Transaction commits: DB writes changes, releases row locks, returns HTTP 200 OK

Why Deadlocks are Physically Impossible: In an opposing transfer (B ➔ A), the algorithm also identifies that ID(A)=101 < ID(B)=205, so it also attempts to lock Account 101 first. Since both threads lock in identical sequence, circular waiting is eliminated — the second thread simply waits cleanly for the first thread to commit.

5. Core Technical Interview Q&A

Q1: Why did you choose Pessimistic Locking over Optimistic Locking for transfers?
"Optimistic locking (@Version) works best in read-heavy applications with low contention because it detects conflicts late and throws an OptimisticLockException. In high-velocity financial systems, however, failing transactions and forcing clients to retry degrades throughput and user experience. Pessimistic write locking queues transactions at the database row level, guaranteeing deterministic, zero-retry completion."
Q2: How is exception handling and input validation architected?
"We created a centralized GlobalExceptionHandler annotated with @RestControllerAdvice. It catches domain exceptions like InsufficientBalanceException (400), ResourceNotFoundException (404), and DuplicateResourceException (409), converting them into uniform JSON responses. We also capture MethodArgumentNotValidException to extract field-level validation errors into a structured error map."
Q3: How is the application containerized and deployed?
"We implemented a multi-stage Dockerfile. Stage 1 compiles the application using Maven and Java 17. Stage 2 copies only the production JAR into an Alpine JRE image running under a dedicated non-root user. Our docker-compose.yml orchestrates the Spring Boot service alongside MySQL 8, with persistent volumes and health checks (mysqladmin ping) ensuring clean startup order."
Q4: How did you test and verify endpoint contracts?
"We have two comprehensive testing suites: (1) JUnit 5 and Spring MockMvc integration tests that execute the full flow from customer creation to transfer assertion, and (2) an automated Postman Collection that chains requests using dynamic environment variables and validates HTTP status codes and JSON schema integrity."
